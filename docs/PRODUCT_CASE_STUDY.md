# DataQuery Agent｜Product Case Study

> 历史演示版本文档。下文保留该阶段原始表述；最新版代码、结果与范围见[版本与数据索引](VERSION_INDEX.md)，演进关系见[迭代历史](ITERATION_HISTORY.md)。


## 1. Product Problem

业务人员希望直接用自然语言查询经营数据，但传统 BI 与 SQL 工具要求专业知识。LLM 可以降低输入门槛，却可能在指标口径、时间范围或业务对象不明确时静默猜测，并返回表面合理的错误答案。

项目希望验证的不是“模型能不能生成 SQL”，而是：

> 如何把 LLM 的开放语言理解约束为一个对业务用户可解释、可追问、可拒绝、可审计的数据产品？

## 2. Target User

- 需要临时查询商业地产经营数据的业务人员；
- 能描述业务问题，但不需要理解数据库结构或 SQL；
- 需要知道系统采用了什么口径，以及为什么要求澄清或拒绝。

## 3. Key User Risks

1. **Silent guessing**：模糊表达被模型自动绑定到单一指标。
2. **Schema hallucination**：用户提出数据库不支持的对象，模型仍然生成查询。
3. **Over-intervention**：系统为了避免错误，对本可执行的问题反复追问。
4. **Unverifiable answer**：用户只看到答案，无法判断模型如何理解问题。

## 4. Product Principles

- 不确定性必须转化为显式产品动作，而不是隐藏在模型推理中。
- 模型负责提出结构化理解，确定性代码负责最终执行权限。
- 澄清与拒绝是产品能力，不是失败兜底文案。
- development 测试、模型冒烟和用户验证必须分别记录。
- 失败结果必须保留，用于驱动下一轮产品决策。

## 5. Solution Design

系统把一次问数拆成五层：

1. **Resolver**：把原始问题拆分为结构化语义片段。
2. **Semantic Gate**：检查原文覆盖、角色边界、指标目录、歧义与安全规则。
3. **Action Router**：选择执行、披露后执行、澄清或拒绝。
4. **SQL Pipeline**：生成候选 SQL，执行只读校验与有限纠错。
5. **Trace & Evaluation**：保留每次尝试、错误与产品动作，支持 Bad Case 复盘。

## 6. Iteration Decisions

### Phase 7–8：规则扩张没有解决开放表达

规则可以拦截已知错误，但不断增加同义词会造成维护成本，并且仍无法判断新表达。项目因此停止把“更多词表”当作主要路线。

### Phase 9A：从词表路由转向可审计语义协议

引入结构化 Resolver 和 Semantic Gate。每段原文必须被完整、无重叠地认领；危险写请求在模型调用前拒绝；模型输出不能直接获得执行权。

### Phase 9B：真实模型暴露协议摩擦

第一版要求模型返回字符 offset，真实运行中大量失败来自 offset 与文本覆盖不一致。产品判断并非“模型不够聪明”，而是协议把不必要的机械负担交给了模型。

### Phase 9B v2：去除 offset，但语义风险仍存在

改为有序原文分段，由代码恢复位置。冻结的 28 题 development 冒烟共使用 40 次真实模型调用：

- 首次严格协议合规：14/27 个模型路由题；
- 最终动作匹配：18/28；
- 预期语义路径匹配：16/28；
- 两条真实歧义问题被静默执行；
- 三条可执行问题被过度干预。

因此版本被阻止进入 SQL 或用户测试。这个决策体现了项目的核心产品原则：安全性不仅是“没有写数据库”，还包括“不把错误理解包装成可信答案”。

### Phase 9C：最小、可解释的修复

Phase 9C 没有重写架构或修改 Gold，而是针对已观察 Bad Case 做最小改动：

- 将指标目录中的歧义规则注入 Resolver；
- Gate 独立阻止已知歧义表达静默绑定到单一指标；
- 区分“不支持的业务概念”“无法理解的文本”和“解析耗尽”；
- 保留旧冻结运行结果，并让旧 runner 因哈希变化而失效，防止复用过期授权。

当前 123 项自动化测试通过。该结果是离线机制证据，不是新的真实模型或用户验证。

## 7. What I Built

- 产品范围、用户风险和四路行为模型；
- 指标目录、业务同义词与歧义规则；
- Resolver / Semantic Gate 协议与错误文案；
- Text-to-SQL 只读执行与有限纠错链路；
- 冻结题集、哈希、调用预算和不可变结果记录；
- development 冒烟分析、Bad Case 复盘与 Phase 9C 优先级决策；
- Streamlit 产品 Demo 与 Trace 展示。

## 8. Evidence Boundary

### Completed

- 独立的本地 DataQuery Agent 原型；
- Phase 9C 离线机制实现；
- 当前 123/123 自动化测试通过；
- Phase 9B 与 Phase 9B v2 冻结 development 冒烟及独立复核。

### Measured

- 28 题 Phase 9B v2 development 冒烟；
- 40 次真实模型调用；
- 动作匹配、语义路径、协议合规、Bad Case 与调用证据。

### Not Yet Validated

- Phase 9C 的新真实模型结果；
- 未见集上的泛化表现；
- 真实业务用户可用性；
- 工作效率、决策质量或商业价值提升；
- 生产环境的延迟、成本、权限和稳定性。

## 9. Next Validation

1. 为 Phase 9C 创建新的独立题集并冻结协议；
2. 在不复用旧授权的前提下完成有限真实模型测试；
3. 优先观察静默执行、过度干预和澄清文案质量；
4. 机制通过后再进行小规模任务型用户测试；
5. 用任务完成、澄清成本和错误理解率评价产品价值，而不是只看 SQL 命中率。
